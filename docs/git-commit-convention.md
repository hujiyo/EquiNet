# Git 提交信息规范

---

- **[feat]** - 新增功能或特性
  - 示例：`[feat] 添加用户导出CSV功能`
  - 场景：代码中有实质性的业务逻辑增加

- **[refactor]** - 代码重构（改变实现，不改变功能）
  - 示例：`[refactor] 优化用户查询逻辑，使用Builder模式`
  - 场景：改进代码结构、性能，但对外接口和行为不变

- **[fix]** - 修复bug，无结构/思路变化
  - 示例：`[fix] 修复登录时间戳计算错误`
  - 场景：纯粹的逻辑错误修复，不涉及架构调整

- **[perf]** - 性能优化
  - 示例：`[perf] 使用索引优化订单查询，减少50%耗时`
  - 场景：明显的性能提升，需要量化说明

- **[style]** - 代码风格调整（不影响逻辑）
  - 示例：`[style] 统一imports顺序，调整缩进`
  - 场景：格式化、linter修复、变量命名规范化

- **[indifferent]** - 微小改动，改动意义有限
  - 示例：`[indifferent] 注释补充，删除冗余空行`
  - 场景：琐碎的改动，改或不改影响不大

- **[docs]** - 文档更新
  - 示例：`[docs] 更新API文档中的错误参数说明`
  - 场景：README、API文档、注释等文档类改动

- **[chore]** - 工程化改动（配置、依赖等）
  - 示例：`[chore] 升级webpack到5.0`
  - 场景：更新构建配置、依赖包、CI/CD配置

- **[test]** - 测试用例增加或修改
  - 示例：`[test] 添加用户登录场景的单元测试`
  - 场景：新增/修改测试代码

- **[verify]** - 验证/验证码相关
  - 示例：`[verify] 修复邮箱验证逻辑`
  - 场景：专门用于验证流程的bug修复

- **[hotfix]** - 线上紧急修复
  - 示例：`[hotfix] 修复支付模块导致订单失败的bug`
  - 场景：生产环境严重问题紧急修复

- **[breaking]** - 破坏性更改（API不兼容）
  - 示例：`[breaking] 修改用户认证接口返回结构`
  - 场景：重大版本升级、API变更

- **[exp]** - 实验性代码（不改变功能，用于测试新功能）
  - 示例：`[exp] 新增成对余弦相似度回归（SIM）的预训练嵌入验证脚本，用于验证"输入空间相似度保真"的几何训练思路`
  - 场景：测试新功能，不改变外部行为


## 提交信息格式

```
[标签] 简述说明

详细说明
```

## 标签选择决策树

```
我的改动是：
│
├─ 新增代码/功能？→ [feat]
│
├─ 修复bug？
│  ├─ 只是修复，没改架构 → [fix]
│  ├─ 线上紧急 → [hotfix]
│  └─ 破坏兼容性 → [breaking]
│
├─ 代码重构/优化？
│  ├─ 性能优化 → [perf]
│  └─ 结构重构 → [refactor]
│
├─ 微小改动？
│  ├─ 代码风格 → [style]
│  ├─ 意义有限 → [indifferent]
│  └─ 测试代码 → [test]
│
├─ 文档/工程化？
│  ├─ 文档更新 → [docs]
│  └─ 配置/依赖 → [chore]
│
└─ 验证相关？→ [verify]
```


## 按场景的标签速查表

| 场景 | 标签 | 说明 |
|------|------|------|
| 用户反馈的功能问题 | `[fix]` | 纯逻辑错误 |
| 性能问题导致超时 | `[perf]` | 需体现优化效果 |
| 代码逻辑不清楚重新写 | `[refactor]` | 外部行为不变 |
| 新的业务需求 | `[feat]` | 增加新能力 |
| 格式化或lint | `[style]` | 不改逻辑 |
| 改个变量名或空行 | `[indifferent]` | 改动微小 |
| 添加单元测试 | `[test]` | 测试代码 |
| 更新README | `[docs]` | 文档相关 |
| 更新package.json | `[chore]` | 工程化相关 |
| 线上故障紧急修复 | `[hotfix]` | 需紧急发版 |
| 改变API返回结构 | `[breaking]` | 版本升级 |
| 修复短信/邮箱发送逻辑 | `[verify]` | 验证流程相关 |


## 常见问题

**Q: 一次提交既修复bug又优化性能，用哪个标签？**
A: 增加多个标签，例如 `[fix] [perf]`。表示这次提交同时包含了修复bug和性能优化两方面的改动。

**Q: [indifferent]是否应该尽量避免？**
A: 是的。如果改动真的有意义，应该用更具体的标签。`[indifferent]`用于那些"整理卫生"类的改动。

**Q: 是否需要在PR标题也加标签？**
A: 推荐在PR标题中也加标签，保持一致性。

**Q: 发现old commit的标签用错了怎么办？**
A: 用`git rebase -i`修改历史，或在新提交中修正。
